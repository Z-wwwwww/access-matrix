## 0. 認証 / ログイン方式（Auth / Login）

| 方式 | 说明 |
|---|---|
| **OIDC SSO** | 主路径。各租户对应一个 Keycloak realm;平台运维用 `system` realm。登录后 JWT 带 `tid`(租户)。 |
| **Break-glass 密码登录** | SSO 不可用时的应急通道(`AdminAuthController` HS256)。`mode=oidc` 下 `/auth/login` 成功即视为 break-glass,会写审计 `system/auth.breakGlass` + 给本人发告警邮件。仅 super-admin 的 `password_hash` 被保留。 |
| **安全模式** | `app.security.mode` = `oidc`(默认) / `jwt`(legacy 密码) / `permit-all`(裸跑无 IdP)。 |
| **租户解析** | `utils/tenant.js` 的 `resolve()` 优先级:`?tenant=`(命中即写入 localStorage 粘住)→ 子域名(生产;命中也粘住)→ localStorage 里的既有值 → `DEFAULT_TENANT`。**兜底值是 `demo` 不是 `default`** —— 租户 `default` 自 V25 改名后就不存在了,别按这个名字去排查。注意查询串**优先于**子域名:URL 上残留一个 `?tenant=xxx` 会盖掉子域名解析结果。 |
| **会话维持** | 双模式。SSO 模式:KC access token(30 min)+ KC refresh_token(SPA 持有,`kc_refresh_token`),到期前 ~2 min 主动续期(`stores/auth.js` 定时器,直打 KC token endpoint,同时重置 KC SSO 空闲计时——开着的标签页不再 30 分钟被踢回 KC 登录页,直到 `ssoSessionMaxLifespan` 才需重登);密码/break-glass 模式:refresh token HttpOnly cookie 走后端 `/auth/refresh`。两条路都受 401 单飞刷新 + 原请求重放兜底;刷新失败(KC 会话真正结束 / 被踢)踢回登录。支持会话(impersonation)期间不续期(避免覆盖 support token)。依赖 realm `revokeRefreshToken=false`(多标签页并发续期不互踢)。 |
| **入驻** | 业务租户管理员:邀请邮件 + 落地页设密;平台运维用户:一次性临时密码(KC 强制首登改密)。 |

**测试点**
- [ ] SSO 正常登录(各租户 + system),登录后能进对应首页。
- [ ] SSO 不可达时,登录页出现"使用应急密码登录"通道;break-glass 登录成功。
- [ ] **破玻璃之后不会被拖去 KC(bug 修复)**:让 KC **可达但慢**(例如给 `/.well-known/openid-configuration` 加 1~2s 延迟),打开 `/login`,在探测还没返回时就连点 5 次热区(或点横幅的"使用应急密码登录")→ 页面**停在密码表单**,不会在随后 1.5 秒被跳去 Keycloak。同理,探测在飞行中时离开 `/login`(如打开 `/invite/{token}`)也不该被拽回 KC。机制:自动跳转是在**探测 resolve 之后**才 arm 的(探测最长 3s,`SSO_PROBE_TIMEOUT_MS`),而那之前根本没有 timer 可清 —— 所以取消动作除了清 timer 还要 latch 一个 `autoRedirectCancelled` 标志,`.then` 里再复查它与 `shouldAutoRedirectToSso()`;`onBeforeUnmount` 也走同一条取消路径。此前只判 `if (autoRedirectTimer)`,于是"慢 KC + 抢在探测期破玻璃"正好落进空窗 —— 而慢 KC 恰恰是最需要破玻璃的场景。
- [ ] break-glass 登录后:`core_oplog` 有 `system/auth.breakGlass` 记录;安全面板"break-glass(7天)"+1;本人收到告警邮件(或日志)。
- [ ] **break-glass 密钥强制(所有模式)**:`CORE_JWT_SECRET` 必须 ≥32 字节且不含任何已知模板标记——`JwtSecretValidator` 对 `dev-placeholder`/`dev-local`/`throwaway`/`change-in-prod`/`do-not-use` 做大小写不敏感的**子串**匹配(不只前缀),故照抄 `.env.example` 的占位密钥(任何环境,含 dev)启动即 fail-fast;oidc 模式下应急通道(HS256)解码器同样挂载,缺失/占位同样拒绝(不再只有 mode=jwt 才校验)。设置合法强随机值(`openssl rand -base64 48`)后,break-glass `/auth/login` 各租户均可用(业务租户登录不再误报 `tenantSuspended`)。
- [ ] **租户隔离的 Java 侧兜底也必须 fail-closed(bug 修复)**:把 `application.yml` 里整个 `app.mybatis` 段注释掉后启动 → 租户隔离仍然**生效**(跨租户查不到别家数据),不是静默放开。此前 `AppMybatisProperties` 的兜底是 `new Tenant(false)`:配置子树一缺失,MyBatis-Plus 租户拦截器就根本不装,所有查询都不带 `WHERE tenant_id = ?`,**每个租户都能读到其它租户的行**,而且没有任何信号 —— `TenantSchemaGuard` 恰好也被同一个开关关掉(只留一条 INFO)。而 yml 注释、`.env.example`、以及同包 `AppSecurityProperties` 里每一个安全兜底(rateLimit/lockout/refreshCookie.secure 全默认安全值)都在声明相反的约定。真正无租户上下文的 profile 现在必须**显式**写 `false`,这正是 yml 注释原本就规定的。由 `AppPropertiesDefaultsTest` 钉住(同时把 security / cors 的兜底方向一起钉上)。
- [ ] **业务租户 break-glass 不误报停用(bug 修复)**:对业务租户(非 system)用应急密码 `/auth/login` 成功,不再因 `core_tenant` 注册表被租户拦截器误加 `tenant_id` 过滤而返回 `error.auth.tenantSuspended`(`TenantMapper.findActiveByCode` 标 `@InterceptorIgnore`)。
- [ ] **猜不出「这个用户名存不存在」(安全缺口修复)**:对一个**不存在**的用户名连续用错密码打 `POST /api/auth/login`,次数超过 `app.security.lockout.max-failures` → 之后的响应必须变成 **`ACCOUNT_LOCKED`**(「请在 N 秒后重试」),与拿一个**真实**用户名做同样操作**完全一致**;两者在此之前也都只返回通用的 `BAD_CREDENTIALS`。此前 `recordFailure` 与锁定检查**都只在用户行解析成功后才执行**,于是真用户名打够次数会翻成 `ACCOUNT_LOCKED`,假用户名则永远停在 `BAD_CREDENTIALS` —— 每个候选发 `maxFailures+1` 次请求就能读出哪些账号真实存在,而这正是项目**已经**用 `DUMMY_BCRYPT` 空跑比对去堵的那件事(时间侧堵了,锁定状态侧漏了)。顺带一提,不存在的用户名当时**完全不消耗**锁定预算,等于「探测账号是否存在」的流量绕开了为它准备的节流。现改为:锁定检查提到**分支存在性之前**、对标识符生效;未命中用户的分支同样 `recordFailure`。由 `AuthServiceEnumerationTest` 钉住 3 条(未知标识符也计入锁定 / 被锁的未知标识符同样答 `ACCOUNT_LOCKED` / 真实账号密码错的行为不变),修复前前两条红。
- [ ] **失败登录的审计行不会因为输入超长而消失(bug 修复)**:用超长输入打 `POST /api/auth/login` —— 例如 `username` 200 字符、`User-Agent` 4000 字符、`X-Tenant-Id` 200 字符 → `core_auth_login_log` **仍有那一行**(各字段截到列宽:identifier 128 / user_agent 512 / tenant_id 64 / client_ip 64 / failure_reason 128)。此前 `LoginAuditService.record` 与 oplog 是同一个姿势:insert 包在 catch-and-WARN 里(审计绝不能影响登录),于是 Postgres 的「值太长了」**不报错、只是让这条失败登录记录消失**。而这里每个入参都是**未认证**请求可控的 —— `identifier` 就是 `LoginRequest.username`(只有 `@NotBlank`,没有 `@Size`)、`userAgent` 是原始请求头、`tenantId` 是原始 `X-Tenant-Id`;已在真实库上验证 identifier/129、user_agent/513、tenant_id/65 都被直接拒。后果是:Redis 侧的锁定计数照常涨,审计里却一片空白 —— 相当于一个自助的「无痕暴力破解」姿势。修法与 oplog 一致,在唯一写入点按列宽夹取;截断的审计行远好过没有。由 `LoginAuditServiceTest` 钉住。
- [ ] **密码输错一次不会弄丢你原本要去的页面(bug 修复)**:在 `/system/user` 上让会话失效(或直接访问 `/login?from=/system/user`)→ 地址栏是 `/login?from=/system/user`;**先故意输错一次密码**(看到「用户名或密码错误」)→ 地址栏的 `from` 必须**保持不变**;再输对密码 → 应当落到 `/system/user`,而不是首页。此前 axios 响应拦截器里「响应体 code=401」这一支被当成「会话过期」处理:而 `ErrorCode` 给 `BAD_CREDENTIALS` / `INVALID_TOKEN` / `EXPIRED_TOKEN` 的数字码**都是 401**,并且 `BusinessException` 是以 HTTP 200 承载的,所以一次普通的「密码错误」和「会话过期」在这里长得**一模一样**。于是它会带着**当前 URL**再 push 一次 `/login` —— 而当前 URL 就是登录页本身,`from` 被套娃成 `/login?from=/system/user`;登录成功后 `router.replace` 到那个 `/login`,登录页 `onMounted` 发现已登录又 replace 到 `/`,深链就这么没了。顺带它还会 `clearAuth()`,同源多标签页下会把另一个标签页仍在用的 token 从 localStorage 抹掉。同一个文件下方 30 行处、针对 **HTTP 状态码 401** 的那一支早就用 `isAuthEndpoint()` 排除了 `/auth/login`、`/auth/refresh`、`/auth/logout`,只是响应体这一支漏了。修复即补上同一个判定(仍然 reject,错误信息照常由登录页展示)。由 `tests/components/requestAuthEndpoint401.test.js` 钉住 3 条(login 不跳转 / refresh+logout 不跳转 / 普通接口 401 仍然跳转),已实测撤掉判定即 2 条失败。
- [ ] access token 过期后自动刷新、原请求重放成功;刷新失败被踢回 `/login`。
- [ ] **SSO 长会话不被踢(bug 修复)**:SSO 登录后保持页面打开/持续操作超过 30 分钟(access token 寿命),**不**跳回 KC 登录页——前台在到期前 ~2 min 自动用 KC refresh_token 续期(Network 可见对 `/protocol/openid-connect/token` 的 `grant_type=refresh_token` 请求);KC 管理台该用户 Sessions 的 idle 时间被刷新。管理员踢下线/禁用后,续期立即失败(invalid_grant)→ 正常踢回登录,强制登出不受影响。
- [ ] 会话失效(被踢下线 / 停用 / 过期且刷新失败)→ 下次请求(如 `/menu/me`)跳 `/login` 并显示友好「会话已过期或已被登出,请重新登录」,**不**再显示技术性的「Menu load failed — 401」(router 守卫把 401 与真正的 menu 加载错误 5xx/坏数据 分开处理,后者才带 detail 供排障)。
- [ ] **被 JIT 解析器拒绝的请求真的"没有业务用户"(bug 修复)**:让一个被禁用/已删除/已迁出 SSO 的账号(三条拒绝分支任一)带着仍然有效的 token 调 `PUT /api/me/profile`(这是唯一一个**不需要权限**却带 `@OpLog` 的端点)→ `core_oplog` 应当留下一行 `system / profile.update`、其 `user_id` 为 **NULL**;此前是**一行都没有**。原因:`OidcJitUserService` 三条拒绝分支的注释都写着「resolves to no business user → no access」,但 `CoreRequestContextFilter` 只在解析**成功**时才覆盖 userId —— 拒绝时 `RequestContext.userId` 仍是 36 字符的 **Keycloak UUID**(既不是业务身份、也不是"没有身份")。而 `core_oplog.user_id` 是 `character(26)`,已在真实库上验证 36 字符的 KC UUID 被直接拒(「对于字符类型来说这个值太长了(26)」),`OpLogService` 又把 insert 失败吞掉 —— 于是这次请求的审计行整条消失。修法在**产生错误值的地方**:拒绝即把 userId 置空(该列可空,已查证),而不是在下游截出一个无意义的 26 字符前缀;顺带消掉「某个免权限端点将来按 userId 取数」这个长期隐患。业务影响仅限审计:该 userId 匹配不到任何行,所以写操作本来就是空操作,`/menu/me` 返回空菜单 → 前端照常登出。由 `CoreRequestContextFilterTraceIdTest` 钉住 2 条(拒绝→null、成功→业务 ULID)。
- [ ] **已登录用户被删除后刷新页面 → 直接登出到 `/login`(bug 修复)**,而非 404。删除后其 token 解析不出可用菜单(角色已解绑;且旧业务行 `mark=0`),`/menu/me` 返回空菜单 → router 守卫检测到「无 home / 无可用路由」即 `clearAuth` + 跳 `/login`,不再注册空 layout 让刷新路径落到 404 兜底页。
- [ ] **邮件落地页在未登录状态下可直接打开(bug 修复)**:退出登录(或用无痕窗口)后,直接访问 `/invite/{token}` 与 `/reset-password/{token}` 都应渲染各自的设密页面,**不**被 router 守卫弹回 `/login`。`/reset-password/` 尤其关键——它是 SSO → 密码反向迁移邮件(`SsoToPasswordMigrationService`,链接为 `CORE_APP_BASE_URL + /reset-password/{token}`)的落地页,收件人按定义还没有密码、根本无法登录,漏掉白名单会让整条重置链路走不通。守卫的公开路径集合由 `router/index.js` 的 `isPublicPath()` 单点判定,并由 `tests/components/routerPublicPaths.test.js` 钉住。
- [ ] **登出页不会把自己写进登录后的跳转目标(bug 修复)**:SSO 模式下正常登出一次(浏览器会经 KC 的 end_session 回到 `/login`),然后按**浏览器后退**退到 `/signout` → 应当直接渲染登出页并落到 `/login`,而**不是**被守卫弹成 `/login?from=/signout`;此时再登录,应当进首页,而不是**立刻又被登出一次**。此前 `/signout` 是唯一一个没进 `WHITE_LIST` 的静态、与会话无关的页面(`/login`、`/sso/callback`、`/invite/{token}`、`/reset-password/{token}` 都在),而 `login/index.vue` 是把 `route.query.from` **原样**replay 的 —— 于是「无会话访问 /signout」这条路会给下一次成功登录埋一个自动登出,界面上不给任何解释、除了手改 URL 没有别的出路。无会话访问 /signout 并不罕见:后退按钮(SSO 登出用的是 `window.location.assign`,`/signout` 留在历史里;密码模式用 `router.replace` 所以不会)、书签,或者 token 已被 `request.js` 的 401 处理清掉的陈旧标签页。无会话访问本身是安全的:`logoutApi()` 的 401 落进它自己的 catch、`clearAuth()` 幂等、`keycloakLogoutUrl()` 在没有 id_token 时会退回带 `client_id` 的形式,最终仍然停在 `/login`。`routerPublicPaths.test.js` 增加 `/signout` 一行(公开集合共 5 条)。
- [ ] **非 demo 租户的邀请/重置链接不再一律「无效或已过期」(bug 修复)**:给一个**非 demo** 租户(如 `sozonext`)的用户发邀请,用**邮件里的链接原样**打开(即从全局 `CORE_APP_BASE_URL` 的域名进,不带 `?tenant=`、localStorage 也是空的,例如无痕窗口)→ 应正常进入设密页并能设成密码;`/reset-password/{token}` 同理。此前这四条语句(两张表各 `findActiveByTokenHash` + `markUsed`)**都没有 `@InterceptorIgnore`**,而它们的 javadoc 却写着「hand-written @Select —— pre-auth,所以 `RequestContext` 里没有租户」—— 手写 SQL **并不能**豁免租户拦截器。代码库自己在 `TenantMapper.findActiveByCode` 的注释里就写明了这条机制:「MyBatis-Plus 租户拦截器改写**所有** SQL —— 包括手写 `@Select` —— 没有 `@InterceptorIgnore` 就会注入 `AND tenant_id = ?`」。而 pre-auth 的上下文租户来自 `X-Tenant-Id`,前端是按**子域名**推的;邮件链接却是用全局唯一的 `app.mail.base-url` 拼的,所以首次收信人(localStorage 为空、域名是 apex/保留标签)会落到兜底值 `demo`。已在真实库上验证:`sozonext` 的 token 用本意 SQL 查得到,加上 `AND tenant_id = 'demo'` 后**查到 0 行**;`markUsed` 的 UPDATE 同样**影响 0 行**,而调用方按约定要把 0 行读成「已使用」。净效果是:**demo 之外每一个租户的邀请链接和密码重置链接都报「无效或已过期」**——而 dev/QA 都跑在 `demo` 上,所以一直看不见。现在四条语句各自加上 `@InterceptorIgnore(tenantLine = "true")`(逐方法,不是类级别;`token_hash` 有 `mark=1` 的全局唯一索引,消费方的租户/用户一律取自**刚认领到的那行**、绝不取自请求)。由 `PreAuthTokenMapperScopingTest` 钉住,并额外断言这个豁免**只**给这两条语句、不许扩到类级别。

- [ ] **业务租户 realm 必须开着 KC 暴力破解防护(安全缺口修复)**:在 KC 管理台看任一业务租户 realm 的 Realm settings → Security defenses → Brute force detection,应为 **启用**;新建一个租户后同样应为启用(模板 `infra/keycloak/realms/demo-realm.json` 的 `bruteForceProtected`,`KeycloakRealmService.createRealmFromTemplate` 克隆它)。为什么必须靠它:oidc 模式下业务用户走的是 **KC 自己的登录表单**,应用侧两道防线都覆盖不到——`AccountLockoutService` 只在 `AuthService.login`(即 break-glass 的 `POST /auth/login`)触发,`AuthRateLimitFilter` 只过滤本服务 URI 里含 `/auth/` 的请求,都碰不到 KC 的 token 端点。此前模板里该开关是 `false`(而 ops 的 `system-realm.json` 是 `true`),等于每个业务租户的密码都可被无限次在线猜测。由 `KeycloakRealmTemplateTest` 钉住渲染后的克隆 JSON。**注意:已按旧模板建出来的 realm 不会被追溯修复**,`KeycloakRealmService` 没有「更新 realm 安全设置」的接口,存量租户需在 KC 管理台逐个打开(或跑一次性脚本)。

## 1. マルチテナント & RBAC 基盤

- **多租户**:业务行带 `tenant_id`;`system` 租户(平台运维)被 MyBatis-Plus 拦截器识别为"绕过租户范围",可跨租户读写。隔离开关 `app.mybatis.tenant.enabled` **两端都 fail-closed**:yml 默认 `true`,且 `AppMybatisProperties` 在整个 `app.mybatis` 子树缺失时也兜底为 `true`(见下测试点)。
- **权限通配符**(`PermissionMatcher`,前后端同源 `frontend/src/utils/permission.js`):`*:*`=平台超级(仅匹配 `platform:` 命名空间);`tenant:*`=租户超级(匹配业务权限,即 `platform:` **与** `opsuser:` 之外);`resource:*`=某资源全动作;精确匹配。两个超级互不覆盖;`opsuser:`(平台用户管理)是独立保留命名空间,`platform:*`/`*:*`/`tenant:*` 都不自动覆盖,只有显式 `opsuser:*` 才命中。
- **角色**:SUPER_ADMIN(各租户,`tenant:*`)、PLATFORM_ADMIN(ops,`*:*`+`opsuser:*`)、PLATFORM_OPERATOR(常规运维,`*:*`)。
- **超管唯一且锁定**:每个业务租户**有且仅有一个** SUPER_ADMIN——即租户新建时邀请的那个用户。该内置「Super Administrator」角色**不可转移**:`UserAdminService.assignRoles` 拒绝把它授予第二个用户(`error.user.superAdminSingleton`);唯一持有者整账号受保护(见下条),其角色绑定任何人都动不了,自然也剥离不掉;内置角色本身已被 `assertNotBuiltIn` 全锁(改名/删除/改权限均拒)。**「同级别」也封堵**:自定义角色不能绑定 `tenant:*`/`*:*` 通配权限(`RoleAdminService.bindPermissions` → `error.role.superPermissionReserved`),避免造出等效超管。前端 `UserEdit` 角色选择器对非持有者隐藏超管角色、对持有者只读;`RoleEdit` 权限选择器对自定义角色隐藏 `tenant:*`/`*:*`。
- **租户管理员账号(=超管用户)在用户管理界面完全只读**:对**其他任何用户**(无论持有什么用户管理权限)整账号不可操作——编辑(含邮箱/显示名)/改角色/改部门/改状态/删除/重置密码/强制登出全部拒绝;管理员**只能本人**在「个人资料」页改自己的邮箱/显示名(`updateOwnProfile`)。识别走后端 `UserDto.View.superAdmin`(以及内置 admin 的 `builtin`)标志位下发,前端 `User.vue` 对该行**直接不渲染任何操作按钮**(操作列为空)。后端硬守卫:`UserAdminService` 各变更方法统一走 `assertNotProtectedAdmin`(`error.user.adminProtected`);该守卫同时**取代了旧的「最后一个超管」守卫**——唯一超管整账号动不了,租户恒有一个可用超管。(回归:此前 `update` 仅锁部门/状态、邮箱/显示名对任何 user:update 持有者开放,且 `changeDept` 完全没拦超管。)
- **不能在用户管理里操作自己 + 自助改资料走个人页**:用户管理控制台对**调用者自己那行**拒绝一切变更(编辑/删除/停用/强制登出/改角色/改部门)——后端 `UserAdminService` 各变更方法首行 `assertNotSelf`(`error.user.selfManagementForbidden`),前端 `User.vue` 按 `isSelf(row)=row.id===authStore.userId` 禁用该行所有按钮 + 提示「请在个人资料页管理自己」。这同时堵两个坑:**自我提权**(给自己加角色)和**自我锁死**(停用/删除/踢自己)。自助改自己**邮箱/显示名**改走「个人资料」页(`Profile.vue` 现可编辑 → `PUT /user/me/profile` → `UserAdminService.updateOwnProfile`,仅联系字段,登录即可、无需细权限);部门/状态/角色仍只能由管理员改。
- **改邮箱/显示名同步 Keycloak**:租户用户管理「编辑」(`UserAdminService.update`)和个人资料页自助修改(`updateOwnProfile`)在写本地 DB 前先 `kc.updateProfile`(email 保持已验证、姓名按显示名重切),与平台运维用户管理同一行为;KC 失败则报错且本地不写,两边不漂移。此前租户侧只写本地,KC 一直保留旧值——账号控制台显示旧邮箱,且 KC「忘记密码」邮件会发往**旧地址**。KC 未启用或该行无 `keycloak_id` 时跳过。
- **编辑路径也做邮箱重复预检**:邮箱可用于登录(`findByIdentifier` 匹配 `email = ? … LIMIT 1`),重复会导致邮箱登录命中歧义。三条编辑路径(租户管理员编辑 / 个人资料自助修改 / 平台运维用户编辑)现与 create 一样做租户内精确预检(排除被编辑行自身),命中抛 `error.user.emailExists` / `error.opsuser.emailExists`(按语言显示);预检在 KC 同步**之前**,KC 不被触碰。此前编辑路径无预检——OIDC 模式仅靠 KC `duplicateEmailsAllowed=false` 兜底(报错笼统误导),legacy password 模式则能直接把重复邮箱写进库。
- **管理员重置业务用户密码(与平台侧同一流程)**:用户管理「重置密码」**不再让管理员输入新密码**——`POST /admin/user/{id}/reset-password`(权限 `auth:reset-password`)由后端生成一次性临时密码:OIDC 模式写入 **Keycloak**(`temporary=true`,首登强制自设新密码;本地 `password_hash` 不动,维持 as-if-always-OIDC 不变式);legacy password 模式才落本地 hash。同时 `terminateUser` 踢下线(拒旧 token + 结束 KC 会话)+ 尽力发「密码重置」邮件(`user-direct-welcome` 模板 reset 文案,走应用 `CORE_MAIL_*`),临时密码**只回显一次**(前端一次性抽屉 + 复制按钮,与平台运维用户管理同款 UX)。对自己、内置 admin、租户超管均拒绝(`selfManagementForbidden` / `adminProtected`)。旧的「管理员手输新密码」端点 `/admin/auth/reset-password` 已删除;**自助改密入口只保留在右上角用户菜单**(KC 账号控制台;超管另有 break-glass)。
- **新建租户自动获得细粒度权限目录**:`RbacSeederService.seedDefaultsForTenant` 除了种 `tenant:*` + 超管角色,还按 `PermissionRegistry` 把**业务侧**(非 `platform:`/`opsuser:`,即 module≠`platform`)的细粒度权限全部种进该租户的 `core_rbac_permission`,这样租户管理员能给自定义角色配权限。**权限目录仍按租户存**(`demo`/业务租户=业务权限,`system`=平台权限),天然隔离平台/业务。此前新租户只有 `tenant:*`——又对自定义角色隐藏——导致角色权限选择器全空、自定义角色拿不到任何权限。**新增功能的权限自动同步到所有租户**:`TenantPermissionCatalogReconciler`(启动期 `ApplicationReadyEvent`)遍历所有业务租户、对每个调用幂等的 `seedPermissionCatalog`,所以加完新页面/功能(新增 `@RequiresPermission` 常量)**重启后端**后,新权限码会自动出现在**每个已有租户**的角色权限选择器里(不再只对新建租户生效)。`system` 租户跳过(平台运维目录);新增只插不删,与 `PermissionConsistencyGuard` 的跨租户孤儿清理(只删代码里已移除的)互补。
- **无可用菜单时不再无限跳转**:零权限/未分配角色的用户登录后,菜单为空 → 守卫清登录态跳 `login?reason=no-access`(区别于 `session=expired`),登录页**不再自动重定向 SSO**(否则 KC 静默重登→菜单仍空→死循环),而是停在登录页提示 `login.message.noAccess`「账号暂无可访问页面,请联系管理员分配角色」。真正的会话过期(401)仍走 `session=expired` + 自动 SSO(有菜单则无缝重登)。
- **菜单**:全局一套(`core_rbac_menu`,无 tenant_id),按 `permission_code` 过滤;前端由 `menu-to-routes` 动态注册路由。
- **数据范围(data scope,部门级行可见性)**:范围定义在**角色**上(`core_rbac_role.data_scope`,字典五模式:ALL / 本部门+子 / 本部门 / 仅本人 / 自定义部门)。请求时 `DataScopeResolver` → `DataScopeQueryService.loadDecision` 算出 `{unrestricted, visibleDeptIds, selfOnly}`:多角色**取并集**(更宽松),任一 ALL 角色或 `*:*` 短路为全可见;部门子树按 `core_rbac_dept.path` 物化路径一条 LIKE 展开;CUSTOM 按角色绑定部门(各含其子树)、与用户自身部门无关;Caffeine 按 userId 缓存 5min,改角色/调部门经 `PermissionCacheService.evictUser` 即时失效。SQL 落地是服务层**显式**调 `DataScopeHelper.apply(wrapper, decision, deptCol, creatorCol)` → 独立 AND 组 `(dept_id IN (可见部门) OR create_user = 本人)`;零范围 → `1=0` 全拦(fail-closed)。**fail-closed 的两个推论**:① 无部门用户的 DEPT/DEPT_AND_SUB 角色贡献为零(只持这类角色 → 看不到任何行);② `dept_id=NULL` 或 `create_user='system'` 的行(程序自动生成且未归属)对所有受限用户不可见、仅 ALL/超管可见——自动写入的数据落库时应显式归属 `dept_id`/`create_user`。数据行的 `dept_id` 创建时盖章、**不跟人走**:用户调部门后旧部门行默认不可见(例外:SELF 看自己创建的、新部门是旧部门祖先、CUSTOM 含旧部门、ALL)。防遗忘:Mapper/服务方法标 `@DataScope`,`DataScopeAspect` 校验 wrapper 经过了 apply(dev/test 拒绝、prod WARN)。**CUSTOM 绑定的失效防护**:部门**删除**时统计 `role_dept` 引用并 IN_USE 提示(force 删除级联清绑定);部门**停用**(status 1→0)同样统计引用、有 CUSTOM 角色引用时 IN_USE 提示「N 个角色把该部门设为自定义数据范围」、确认后 force 重发才停用;解析时绑定指向**已删除**(mark=0)部门的条目贡献为零(fail-closed,不再裸加 id);RoleEdit「数据部门」tab 会把"已绑定但不在树里"(停用/删除)的部门列成**失效绑定警告区块**(琥珀色),可单个或全部移除。行级可见性与功能权限(`@RequiresPermission`)正交;租户隔离在更外层(MP 租户拦截器)。详例:`docs/data-scope-demo`。

**测试点**
- [ ] 业务 super(`tenant:*`)看不到平台菜单 / 调 `/platform/*` 返回 403。
- [ ] 平台 ops(`*:*`)能管租户但不能模拟业务用户(无 `tenant:*`)。
- [ ] **踢出/禁用/删除/重置密码会结束 KC 会话(bug 修复)**:业务用户被禁用/删除/踢下线/重置密码后,被踢者在登录跳转页**不会被 SSO 静默重新登录**——`UserAdminService` 经 `SessionTerminationService.terminateUser` 同时 `kickOut`(拒旧 token)+ `kc.logoutUser`(结束 KC 会话,逼真正重新认证)。此前只 kickOut、KC 会话还在,跳转即被静默重登,踢出形同无效。

## 3. 共通基盤（Cross-cutting）

- **时间模型(V58)**:全链路**绝对时刻**——DB 列 `timestamptz`、后端 `OffsetDateTime`(实体/DTO/`now()`,禁用 `LocalDateTime`,由 ArchitectureTest 守护)、wire 为 ISO-8601 **带偏移量**字符串(双向,前端发送走 `toBackendDate`)。业务时区只出现在边缘:前端显示(`@/lib/date` 的 `toJST*`,`VITE_DEFAULT_TIMEZONE`)与墙钟决策(后端 `AppTime.zone()`:cron 触发、日/月聚合 SQL 的 `AT TIME ZONE`、取号日期、邮件内时间文案)。面向**多国独立部署**:业务时区为部署级配置 `app.timezone`(env `CORE_TIMEZONE`),默认 `Asia/Tokyo`,非法 IANA id 启动即失败(`AppTimeConfigurer`);前后端两个时区配置应配成同一个值。显示结果与部署机器/浏览器时区无关。
- **字典(Dictionary)**:内置枚举字典 + 运行时可编辑的管理字典;前端 `useDict`,下拉/标签均走字典,不硬编码。`/platform/dicts` 管理。
- **操作审计(oplog)**:`@OpLog` 写 `core_oplog`;失败行带 `error_code`(BusinessException 的 4xx/7xx vs 未预期 500)。
- **领域事件出箱**:状态变更在同一事务 `EventPublisher.publish(...)` → `core_domain_event` → `OutboxDispatcher` → 可插拔 sink(当前为日志兜底)。详见 backend/AGENTS.md。
- **通知(铃铛)**:`core_notification` + SSE 心跳(15s)。注意与领域事件是两套东西。
- **编号(numbering)**:`core_numbering*`,按租户分配 user_no 等。**唯一的发号入口是 `NumberingService`**(原子 `UPDATE ... RETURNING`),任何路径都不得用 `MAX(业务列)+1` 自己算下一个号 —— 见 V59。
- **i18n**:ja_JP / zh_CN / zh_TW / en / ko_KR 五语;权限标签由后端 `I18nPermissionPatcher`(仅 dev)生成占位 `__TODO__`,需人工填 `frontend/src/lang/generated/permissions.*.json`。frontend 目录从 `user.dir` 向上逐级以 `package.json` 探测定位(兼容 IDEA 模块运行 / `spring-boot:run` 等不同工作目录),找不到时跳过且**不创建任何目录**;另一仓库布局可用 `app.permission.i18n.frontend-dir` 配绝对路径。
- **邮件品牌 logo**:所有邮件模板(`user-invite` / `user-direct-welcome` / `user-password-reset` / `user-break-glass-used`,各 5 语言)header 含品牌 logo;**外链 PNG** `${baseUrl}/access_matrix_logo.png`(由 `frontend/public/access_matrix_favicon.svg` 渲染成位图——邮件客户端不显示 SVG)。`MailService` 对每封邮件统一注入 `logoUrl`(`putIfAbsent`,调用方可覆盖)。

## 4. フロントエンド基盤（Frontend foundation）

- **多 Tab + keep-alive**:目录占位 `EmptyLayout` 单实例复用(修复了"多 tab 后新 tab 发重复请求")。
- **Tab 栏(Browser 风)**:`AppTabBar`。非激活 tab 之间用 `::before` 竖分割线分隔(相邻激活/hover 时隐藏);tab `flex-1 min-w-[56px] max-w-[120px]` + `truncate` 均匀缩小;缩到极限不向右延伸,多出的收进右侧 `+N`(`ResizeObserver` 测宽算 `visibleCount`,始终保证 active 可见),hover `+N` 弹出隐藏 tab 列表;标题被截断时 hover 在 tab 下方弹完整名 tooltip(`pointer-events-none`,Teleport 到 body 避免被裁,仅 `scrollWidth > clientWidth` 时弹)。拖拽排序 / 右键菜单 / 末端批量操作保留。
- **详细 tab 业务标识**:`tabsStore.tabExtras`(**不持久化**的内存 map,`fullPath → {prefixKey, badge}`)+ `setTabExtra`。业务详细页在自身 `loadDetail` 内调用(切忌用依赖全局 route 的 watch,keep-alive 缓存下会污染别的 tab);`tabLabel` 读它把 `予約番号/施設名` 等业务标识拼到「XX-詳細」后,`prefixKey` 存 i18n key 以跟随语言。基盘暂无业务详细页,此为预置基础设施。
- **确认弹窗**:全项目用 `useConfirm()` 的 `confirm()`(Promise)+ 常驻 `<ConfirmDialog>`(无 `window.confirm`);`ConfirmDialog` z-index = `z-[100]`,高于 `Dialog`(`z-[90]`),保证从 Dialog 内触发删除时确认框可见可点(否则被遮 → Promise 永不 resolve → "点击无反应")。
- **侧边栏**:收藏 / 置顶 / 顶层叶子菜单提升 / 折叠 flyout。
- **主题 / 调色板**:CSS 变量;`.dark` + `data-palette`。单一暖色主题(暖米白 `#f4efe9` 背景 + 纯白卡片 + 页面背景两团极淡品牌径向光晕,深色模式去掉光晕),仅**品牌强调色**可切:陶土铁锈(默认)/ 砖红 / 赭黄 / 暗松绿 / 灰紫;surfaces 五色共用,只换 `--primary/--accent/--ring/--brand-orange`。**深色用 `.dark` class 切换**(`useTheme.js`),`main.css` 必须配 `@custom-variant dark (&:where(.dark, .dark *))`,否则 Tailwind v4 的 `dark:` 默认跟随系统 `prefers-color-scheme`,"系统亮色 + 手动深色"时全项目 `dark:` 静默失效。主题在 app **启动时即应用**(`main.js` 引入 `useTheme`,模块副作用给 `<html>` 加 `.dark`/`data-palette`),使**未登录的 `/login` 等首屏**也跟随;否则 `useTheme` 只被登录后的 `AppHeader` 引入,登录页会停在亮色、且 SSO 跳转会误传 `ui_mode=light`。
